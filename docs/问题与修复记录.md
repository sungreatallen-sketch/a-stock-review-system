## 经验教训（工程化结论）
1. **外部依赖会变**：端口、域名、限流、网络——必须自动发现/多路兜底/显式上报，不能写死。
2. **一致性靠机制**："用户看到的=结算的""报告完整才复用"靠规则+代码强制，不靠记忆。
3. **合规靠自检**：规则系统能当场抓住未实现缺口与运行时异常（如 I11）。
4. **输出要双口径**：单一口径容易漏信息（开盘 vs 收盘）。
5. **工程基线化**：需求/架构/规则/问题记录全部文档化+git 版本化，变更走流程。
## I32: DeepSeek 研判解析失败

- **发现日期**: 2026-08-18
- **严重程度**: 中（飞书复盘输出标的为空）
- **现象**: 飞书发送"复盘"后，标的推荐显示"LLM研判失败"
- **根因**: DeepSeek API 返回 reasoning_content（推理过程）和 content（最终答案）两个字段。偶尔模型把推理文本混入 content，导致 safe_json 解析失败。json_mode=True 是提示而非保证，LLM 输出不可靠是固有特性。
- **修复**: safe_json 从2层容错增强到5层：直接解析 → 去围栏 → 截取{到} → 修复尾部逗号 → 提取最大完整JSON对象
- **提交**: 597eda6
- **测试**: 7/7 通过（正常JSON/带围栏/带推理文本/尾部逗号/嵌套JSON/空字符串/纯文本）
- **验证**: Bot 已重启，飞书连接正常
- **防复发**: safe_json 是防御性解析，未来 LLM 返回任意格式都能兜底

## I34: 涨停股被推荐但无法买入

  2. strategy.py: 候选池阶段直接过滤掉涨停股
  3. backtest.py: 回测跳过涨停股
- **测试**: 涨停股评分20.2 vs 正常股74.2，过滤有效
- **影响**: 历史命中率和收益率需要重新计算（去掉涨停股后会下降，但更真实）

## I36: 非交易日复盘失败 + 预测标的类型错误

- **发现日期**: 2026-08-24
- **严重程度**: 高（非交易日无法生成预测，影响用户体验）
- **现象**: 
  1. 今天（周一）复盘失败，预测状态为"预测生成失败"，错误信息 `'str' object has no attribute 'get'`
  2. 非交易日（周末）发送"复盘"时，系统返回提示但不生成预测
- **根因**: 
  1. judge.py 中 LLM 返回的 targets 列表可能包含非 dict 元素（字符串），导致 `.get()` 调用失败
  2. workflow.py 在非交易日时直接返回提示信息，不执行预测流程
  3. feishu bot 在非交易日发送警告后仍调用 `_full_report_and_reply`，但 `run_review` 已返回
- **修复**:
  1. judge.py: 添加 `isinstance(t, dict)` 类型检查，跳过非 dict 元素
  2. workflow.py: 非交易日时使用最近交易日继续执行，不返回提示
  3. feishu bot: 修改警告消息为"正在生成报告..."
  4. track.py: 添加 sell_date == pred_date 的异常处理
- **测试**: 待测试
- **防复发**: 类型检查 + 非交易日自动降级到最近交易日

  4. 补 cache.py 缺失的 log 定义
  5. track.py/workflow.py 添加 MCP 响应类型检查
- **测试**: 完整复盘成功生成 3 只标的 + market_view 正常
- **防复发**: MCP 异常不再写入损坏缓存，非 dict 响应归一化

- **测试**: 候选池构建成功（45个候选，change_ratio=float），预测生成3只标的
- **防复发**: 数值字段在入口统一转 float，数据源返回任何类型都能防御
